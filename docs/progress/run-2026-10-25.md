## Phase 1: rate limiting (open questions 4 and 14)

**What I did**
- New package `api/internal/ratelimit`: a small counter per key (for example `login|203.0.113.5`) in a **fixed window**. Standard library only: a `map` protected by a `sync.Mutex`. Finished windows are removed about once a minute, so the map cannot grow forever.
- `api/internal/httpapi/ratelimit.go`: `s.limited(action, limit, handler)` wraps four routes: admin login, place order, track, customer cancel. Over the limit the answer is `429 TOO_MANY_TRIES` with a `Retry-After` header (seconds) and "Too many tries. Please wait a minute and try again." (or "… wait 9 minutes …" when the window is longer).
- The numbers are **settings** (migration `00007_rate_limits.sql`), shown in Admin > Settings under "Too many tries (per IP address)": login 4 per 15 min, orders 30 per 10 min, track 30 per 10 min, cancel 10 per 10 min.
- Login: the per-IP check runs **before** the password check. A refused try never reaches the account lockout, so a stranger's extra tries do not count towards pausing the Owner's account. The old lockout stays as it was.
- Client IP: the direct connection address by default. Only with `TRUSTED_PROXY=cloudflare` **and** the Worker's `PROXY_SECRET` on the request does the API take the IP the Worker passes on (`X-Drakon-Client-IP`, copied from Cloudflare's `CF-Connecting-IP`). IPv6 addresses are grouped by their /64 network.
- Worker (`web/worker/index.ts`), `.env.example`, `docs/deploy.md` (two new Render variables + `npx wrangler secret put PROXY_SECRET`), `docs/api.md` (429 + the limits).
- Commits: `8577c57`, `577a051`.

**Why**
- Without a limit, anyone can try passwords or order numbers as fast as their computer allows, and anyone could pause the Owner's login by typing wrong passwords.

**Key concepts for a beginner**
- **Fixed window:** "at most N tries per 10 minutes". The first try starts a 10-minute window and the count; when the window ends, the count starts again from 0. Simple and enough for a small shop.
- **Why memory is fine now:** the API runs as **one** process on one Render instance, so every request passes the same map. With 2+ instances each would count on its own (a visitor could get 2× the limit), and the counts would have to move to a shared place (PostgreSQL or Redis). A restart forgets the counts, which is harmless.
- **Why not trust `X-Forwarded-For` blindly:** it is just a header. Anyone can send `X-Forwarded-For: 1.2.3.4` and change the number on every request, getting a fresh limit each time. Proxies add it, but so can attackers. So we believe it only from a proxy we can prove is ours: our Worker adds a secret that only Render and the Worker know. The Render address is public, so without the secret anyone could skip the Worker and send fake IPs.
- **Shared IPs:** many phones in Bangladesh share one mobile-network IP (called CGNAT). That is why the shop limits are generous; the Owner can raise them in Settings.
- **`Retry-After`:** a standard header that tells the browser how many seconds to wait.

## Phase 2: payment status VOID (open question 8)

**What I did**
- Migration `00008_payment_void.sql` adds `VOID` to `payment_status`. Migration `00009_void_and_currency.sql` turns the PENDING payment of every order that was **already** cancelled into VOID, and adds `CHECK (currency = 'BDT')` to all six currency columns (audit item A15).
- `orders.CancelLocked` (the one function every cancel uses: buyer, admin, 48-hour sweep) now runs `VoidPendingPayments`: `UPDATE payments SET status = 'VOID' WHERE order_id = $1 AND method = 'COD' AND status = 'PENDING'`. A COLLECTED or REFUNDED payment is never touched, because of `AND status = 'PENDING'`.
- Admin order page: the payment line says **"Cancelled, nothing to collect"**.
- Dashboard and sales numbers already count orders, not payments, and leave out CANCELLED; a new test proves a cancelled order with a VOID payment is not counted.
- Tests: VOID checks in `TestCancelPutsStockBack` (buyer), `TestAdminCancelPutsStockBackWithAdminID` (admin), `TestAutoCancelOldPendingOrders` (sweep), and the new `TestCancelVoidsOnlyPendingPayments`. The migrations were proven on a throwaway database: up, the old cancelled order became VOID, `currency = 'USD'` was refused, down (VOID back to PENDING, the enum without VOID), down to 0, up again.
- Commit: `5d19a0b`.

**Why**
- A cancelled COD order has no money to collect. "PENDING" made it look like cash was still on the way.

**Key concepts for a beginner**
- **Enum:** a column type that allows only a fixed list of words (`PENDING`, `COLLECTED`, …).
- **Why two migration files:** PostgreSQL does not let you *use* a new enum value in the same transaction that *added* it. So 00008 only adds `VOID` (with `-- +goose NO TRANSACTION`), and 00009 uses it.
- **Removing an enum value** is not possible directly; the Down step builds the type again without it.
- **CHECK constraint:** a rule the database checks on every insert/update. Now even a bug in Go could not save a currency other than BDT.

## Phase 3: `make reset-dev` (open question 9)

**What I did**
- `cd api && make reset-dev` (= `go run ./cmd/admin reset-dev`, code in `api/cmd/admin/reset.go`).
  1. Refuses any `DATABASE_URL` whose host is not `localhost` / `127.0.0.1` / `::1` (Neon is impossible), or that has no database name.
  2. Says what it will delete and asks you to type **`reset drakon`** (the word `reset` + the database name). Anything else stops: "not confirmed; nothing was changed".
  3. Empties orders, payments, returns, history, stock movements, blocked phones and the catalogue, then loads `db/seed/dev_seed.sql` again, all in **one transaction**.
  4. Keeps admins (your login), settings, delivery zones and areas.
- Tests (refusal logic only, as asked): `TestResetDevRefusesNonLocalDatabases`, `TestResetDevNeedsTheExactWords`, `TestResetScriptIsOneTransaction`. A refused run never touches the database (the tests pass no database at all).
- I ran it once on a throwaway database `drakon_mig` (made and dropped again): wrong words → stopped; right words → 10 products back, the admin and a changed setting kept. **Never on your `drakon`.**
- Added to `CLAUDE.md` Commands. Commit: `c52eb77`.

**Key concepts for a beginner**
- **TRUNCATE** empties a whole table at once (faster than DELETE). `RESTART IDENTITY` makes the ids start at 1 again.
- **No CASCADE on purpose:** `CASCADE` would also empty any other table that points to these. Without it, a new table that we forgot fails loudly instead of being wiped quietly.
- **One transaction:** the seed file already has `BEGIN; … COMMIT;`. The TRUNCATE is put right after its `BEGIN;`, so if the seed fails, the emptying is undone too.

**How to test it yourself**
```zsh

make reset-dev          # type something wrong first: nothing changes. Then: reset drakon
```
